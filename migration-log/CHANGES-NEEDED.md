## FAQ / Read more / See more audit — 2026-09-11

User asked to verify everything in `FAQ_AND_MORE_BUTTONS_DIRECTORY.md` (11 FAQ sections/99+ questions, 42 "Read more" toggles, 16 "See more" gallery buttons, 3 "Learn more" links) actually works.

- [x] **Critical sitewide bug found and FIXED — `components/AccordionToggle.tsx` silently broke any FAQ/Read-more/Learn-more toggle whose target id starts with a digit.** The click handler called `document.querySelector(targetSelector)` where `targetSelector` is a content-hash id like `#8b62cb6caf25eab40` — `querySelector` throws a `SyntaxError` on an id selector starting with 0-9 (invalid CSS), and since that throw happens before the `e.preventDefault()` line, the whole handler silently failed: no panel opened, and the browser fell through to its default `href="#id"` behavior (a dead anchor-jump) instead. Of the 42 "Read more" toggles alone, 19 target ids start with a digit — all were broken; likely a similar share of the 99+ FAQ answers too (confirmed 9/11 broken on `/doors/bullet-proof-doors` before the fix). Root-caused via live DOM testing (dispatched real click events, checked `defaultPrevented` and before/after `.in` class state), not assumption. **Fix**: swapped to `document.getElementById(targetSelector.slice(1))`, which has no such restriction. Verified after the fix: all 3 toggle types work on `/doors/communal-entrance-doors` (FAQ, Read more, Learn more), including the accordion's sibling-close behavior; all 11/11 FAQ questions on `/doors/bullet-proof-doors` now toggle correctly. `tsc` clean. **Not committed/pushed yet** — awaiting go-ahead.
- [ ] **"See more" gallery buttons (16 total) are non-functional — but this is inherited from the live site, not a migration regression.** Confirmed: plain `<a href="#">See more</a>` with no `data-toggle`, no `onClick`, no handler anywhere in the codebase (`awb-gallery-load-more-btn` isn't referenced by any component). Clicking does nothing but jump to the top of the page. Checked whether this hides real additional photos: compared image counts before/after clicking on both our production-equivalent page and the **live WordPress site itself** (`/door-styles/edwardian-doors`, 7 images) — identical count before and after on both sites. The live site's own "See more" button doesn't load anything either. Not a content-loss bug; left as non-functional to match the original unless the user wants it built into a real feature (would be new scope, not parity).

## Missing parallax background images — 4 door-styles pages — 2026-09-11 — FIXED

User reported no image showing right after the intro paragraph on Georgian, Victorian, Edwardian, and French Doors. Confirmed real: each of these 4 pages (and only these 4 — verified via `grep -rl "fusion-bg-parallax" app` returning exactly this set) has a `.fusion-fullwidth.fusion-parallax-up` section right after the intro text with a `data-bg-url` attribute but no actual `background-image` CSS — Avada's real parallax JS would normally read that attribute and apply the image at runtime, and this migration never pulls that JS in. Root-caused via the page's own compiled CSS (`fusion-styles/*.min.css`): `.fusion-fullwidth` already resolves `background-image: var(--awb-background-image)` (default `none`) — the same CSS variable pattern already used successfully elsewhere in this codebase (e.g. the homepage hero, `--awb-background-size`/`--awb-background-position` already default to `cover`/`center center` so only the image itself was missing). **Fix**: added `'--awb-background-image': 'url("...")'` to each section's existing inline `style` object, reusing the same `data-bg-url` path already present in the markup — no new assets needed. Verified visually and via `getComputedStyle` on all 4 pages: Georgian shows a purple front door with white brick facade, Victorian/Edwardian/French each resolve their correct background image. `tsc` clean. **Not committed/pushed yet.**

### Communal Entrance Doors (`/doors/communal-entrance-doors`) and Colllabsible Grilles (`/grilles-shutters/colllabsible-grilles`) — false alarms, root cause found and fixed
Both flagged by the audit as having "extra" content not on the live site (a 4-card "Versatility for every property type" section on Communal Entrance Doors; a CX1/CX2/VULCAN/ECLIPSE grille-tier spec section on Colllabsible Grilles). **Turned out to be a false alarm, not missing/extra content**: both sections use Avada's "scroll-stack" Swiper widget (`data-animation="stack"`, wrapped in `.fusion-scroll-section`), which normally reveals its cards progressively as the user scrolls, driven by real Swiper JS that this static migration never pulls in (see `DECISIONS.md`, "the Swiper carousel decision" — `/doors/communal-entrance-doors` is explicitly named there as an example). The audit's `get_page_text` check on the live site simply couldn't see cards that only reveal via scroll-linked JS animation — the content is real and present on both sides.

User reported the actual visible symptom directly: cards render side-by-side in a static grid with zero animation (matches the existing global CSS override in `app/layout.tsx` that forces `.swiper-wrapper` into a plain grid, chosen as a "flat but readable" fallback since full Swiper was never installed). Asked the user whether to leave this as-is, add a lighter CSS-only scroll-in reveal (the middle-ground option `DECISIONS.md` already anticipated), or install real Swiper for the exact stack/rotate motion — **user chose the CSS-only middle ground for both pages**.

**Fix**: added `components/ScrollReveal.tsx` (a small client component using `IntersectionObserver`, re-running on every route change via `usePathname()` since the root layout doesn't remount on client-side navigation) plus matching CSS transition rules in `app/layout.tsx` (`.fusion-scroll-section .swiper-slide` starts faded/translated down, gets `.scroll-revealed` added as it scrolls into view). Mounted globally in `app/layout.tsx`, so it applies automatically to **every** page using this pattern, not just these two: `/doors/communal-entrance-doors`, `/grilles-shutters/colllabsible-grilles`, `/garage-doors/sectional-garage-doors`, `/garage-doors/tracless-garage-doors`, `/grilles-shutters/` (hub), `/windows/security-aluminium-windows`. Verified on both `/doors/communal-entrance-doors` and `/grilles-shutters/colllabsible-grilles`: cards fade/slide in on scroll, end fully visible, all 4 slides get `.scroll-revealed`. `tsc`/`build` clean. This is **not** a replica of the live site's exact "stack and rotate upward" motion (that needs real Swiper — bigger scope, not chosen) — it's real entrance motion instead of content just appearing, same spirit as the live site without the exact same mechanism.

**Side effect worth knowing**: this also resolves 2 of the "likely false alarm" items further down this doc (Tracless Garage Doors, Security Aluminium Windows) and the Grilles Shutters hub, since all three use the same `.fusion-scroll-section` pattern and were flagged for the same underlying reason (content that only reveals via scroll-linked animation, invisible to a text-scan check). Attempted to re-verify all 3 directly in-browser: confirmed the elements and markup are structurally identical to the 2 already-working pages, but hit a browser-automation artifact partway through (the automated tab got backgrounded, which Chrome throttles `IntersectionObserver` for — confirmed by testing that even `document.body`, which should always intersect, reported `isIntersecting: false` while `document.visibilityState === "hidden"`) rather than a real per-page bug. Not a concern for actual users (a real, focused tab doesn't have this throttling) — the underlying mechanism is proven on 2 pages and identical on all 6.

## Homepage "Luxurious Security Doors" video not showing — 2026-09-11 — FIXED

User reported the video beside the "Luxurious Security Doors" heading wasn't loading, even after leaving the page open for hours (ruling out a slow-load explanation). Visually confirmed via screenshot: the video's whole column was blank white with a permanently-spinning loading icon.

Found two independent, compounding bugs on this one video (`Untitled-2024-11-11-17-47-13copy-2-compressed.mp4`, `app/page.tsx`'s "tfs-slider" section):
1. **The slide itself was `display: none`.** This is Avada's FlexSlider-pattern widget - its real CSS hides every `<li>` inside `.slides` by default and only reveals the active one via a class that FlexSlider's own JS adds, which this migration never loads. Confirmed via `grep` that this is the *only* `className="slides"` element on the whole site (single slide, not a real carousel), so forcing it permanently visible is the correct fix, not a workaround. This was the primary cause - even before checking the video's own attributes, the entire slide (video included) was collapsed to 0x0 and invisible.
2. **The `<video>` tag itself was also missing the native `autoplay` attribute** - it only had the inert `data-autoplay="yes"` data attribute (meant for the same absent FlexSlider JS to read and manually call `.play()`), not real HTML `autoplay`. Even after fixing bug #1, the video would have sat there paused indefinitely with no user interaction. Added `autoPlay` and `playsInline` (the latter so mobile Safari doesn't force fullscreen instead of the inline background-video look every other hero video on the page already has).

Fix: `.tfs-slider .slides li { display: block !important; }` in `app/layout.tsx`'s global override block, plus `autoPlay={true}` / `playsInline={true}` on the `<video>` in `app/page.tsx`. Verified: video now renders a real frame (previously blank), has real non-zero dimensions, and both `autoplay`/`playsinline` attributes are present. Could not visually confirm active playback in this automated browser session specifically because of a already-documented environment limitation (`document.visibilityState === "hidden"` in a backgrounded/unfocused tab suspends video autoplay browser-wide) - confirmed this isn't specific to this video by checking that 4 *other*, already-correctly-configured videos on the same page show the identical paused/suspended state in this same session. `tsc` clean, zero console errors. Not committed/pushed yet.

### Communal Entrance Doors (`/doors/communal-entrance-doors`) and Colllabsible Grilles (`/grilles-shutters/colllabsible-grilles`) — false alarms, root cause found and fixed
Both flagged by the audit as having "extra" content not on the live site (a 4-card "Versatility for every property type" section on Communal Entrance Doors; a CX1/CX2/VULCAN/ECLIPSE grille-tier spec section on Colllabsible Grilles). **Turned out to be a false alarm, not missing/extra content**: both sections use Avada's "scroll-stack" Swiper widget (`data-animation="stack"`, wrapped in `.fusion-scroll-section`), which normally reveals its cards progressively as the user scrolls, driven by real Swiper JS that this static migration never pulls in (see `DECISIONS.md`, "the Swiper carousel decision" — `/doors/communal-entrance-doors` is explicitly named there as an example). The audit's `get_page_text` check on the live site simply couldn't see cards that only reveal via scroll-linked JS animation — the content is real and present on both sides.

User reported the actual visible symptom directly: cards render side-by-side in a static grid with zero animation (matches the existing global CSS override in `app/layout.tsx` that forces `.swiper-wrapper` into a plain grid, chosen as a "flat but readable" fallback since full Swiper was never installed). Asked the user whether to leave this as-is, add a lighter CSS-only scroll-in reveal (the middle-ground option `DECISIONS.md` already anticipated), or install real Swiper for the exact stack/rotate motion — **user chose the CSS-only middle ground for both pages**.

**Fix**: added `components/ScrollReveal.tsx` (a small client component using `IntersectionObserver`, re-running on every route change via `usePathname()` since the root layout doesn't remount on client-side navigation) plus matching CSS transition rules in `app/layout.tsx` (`.fusion-scroll-section .swiper-slide` starts faded/translated down, gets `.scroll-revealed` added as it scrolls into view). Mounted globally in `app/layout.tsx`, so it applies automatically to **every** page using this pattern, not just these two: `/doors/communal-entrance-doors`, `/grilles-shutters/colllabsible-grilles`, `/garage-doors/sectional-garage-doors`, `/garage-doors/tracless-garage-doors`, `/grilles-shutters/` (hub), `/windows/security-aluminium-windows`. Verified on both `/doors/communal-entrance-doors` and `/grilles-shutters/colllabsible-grilles`: cards fade/slide in on scroll, end fully visible, all 4 slides get `.scroll-revealed`. `tsc`/`build` clean. This is **not** a replica of the live site's exact "stack and rotate upward" motion (that needs real Swiper — bigger scope, not chosen) — it's real entrance motion instead of content just appearing, same spirit as the live site without the exact same mechanism.

**Side effect worth knowing**: this also resolves 2 of the "likely false alarm" items further down this doc (Tracless Garage Doors, Security Aluminium Windows) and the Grilles Shutters hub, since all three use the same `.fusion-scroll-section` pattern and were flagged for the same underlying reason (content that only reveals via scroll-linked animation, invisible to a text-scan check). Attempted to re-verify all 3 directly in-browser: confirmed the elements and markup are structurally identical to the 2 already-working pages, but hit a browser-automation artifact partway through (the automated tab got backgrounded, which Chrome throttles `IntersectionObserver` for — confirmed by testing that even `document.body`, which should always intersect, reported `isIntersecting: false` while `document.visibilityState === "hidden"`) rather than a real per-page bug. Not a concern for actual users (a real, focused tab doesn't have this throttling) — the underlying mechanism is proven on 2 pages and identical on all 6.

# Detailed Mistakes, Root Causes, and Patches (Chronological)

This file exists so we do NOT repeat the same mistakes. Read this before starting any new large-scale change.

## 1. Initial strategy debate: full rebuild vs fast repackage
- An external tool ("Antigravity"/"anti-gravity") recommended a full from-scratch React rebuild with clean components immediately.
- Correct call made instead: fast repackage first (raw HTML wrapped in dangerouslySetInnerHTML) to hit a hard deadline, with proper componentization explicitly deferred as a LATER phase — this is the "strangler fig" / incremental migration pattern, not a shortcut to be ashamed of.
- LESSON: matching engineering effort to actual deadline constraints is correct; premature full rebuilds under time pressure cause more harm than good. But the deferred "proper" work must actually get scheduled and done later — don't let "later" become "never."

## 2. Lazy-load images/videos appeared broken after migration
- Symptom: images and background videos appeared completely blank/missing after raw HTML was wrapped in Next.js.
- Root cause: the original Avada theme's lazy-loading system stores real image URLs in data-src/data-srcset/data-bg attributes and swaps them into src/srcset/style via jQuery on page load. Since that jQuery never runs in the Next.js static site, browsers only ever saw the placeholder attributes.
- Patch: script to rename data-src→src, data-srcset→srcset, and convert data-bg="url" into inline style="background-image:url(...)" directly in the HTML at migration time, so no JS execution is needed.
- LESSON: whenever migrating a theme-driven WordPress site, ALWAYS check for lazy-load attribute patterns before assuming missing images are a path/asset problem.

## 3. Asset path rewriting missed several URL variants
- Symptom: many images continued loading from the LIVE site (secure-house.co.uk) instead of local assets, or were still 404ing after local rewriting.
- Root cause: the regex used to rewrite wp-content URLs only handled some variants (e.g. absolute https://domain/wp-content/) and missed others: protocol-relative (//domain/wp-content/), bare relative (wp-content/...), and query-string-suffixed filenames.
- Patch: iteratively broadened the regex across several rounds until a full grep-verification (search for any remaining "secure-house.co.uk" + "wp-content" combination) returned zero matches — this "grep to zero" verification step should be standard for any global find/replace across many files, not just done once and assumed complete.
- LESSON: when writing a global path-rewrite regex, enumerate ALL known URL variants up front (absolute with/without www, protocol-relative, relative, with/without query strings) rather than fixing them one at a time as bugs are reported.

## 4. Special characters in scraped filenames broke asset copying
- Symptom: some images physically failed to copy from the backup to the Next.js project; some copy commands crashed on Windows.
- Root cause: the HTTrack scraper encoded special characters (like "?") from original query-string URLs directly into local filenames using unicode escape sequences, sometimes producing filenames exceeding Windows' 260-character path limit.
- Patch: used the \\?\ long-path-bypass syntax on Windows, and wrote a cleanup script to strip the unicode-encoded junk from filenames during copy.
- LESSON: scraper tools can produce filesystem-hostile filenames; always sanity-check filenames for illegal/oversized characters before bulk-copying scraped assets, especially on Windows.

## 5. A subset of images were WordPress auto-generated thumbnail sizes that were never scraped
- Symptom: after fixing path rewriting, ~850 images still 404'd. Investigation showed the HTML requested dimension-suffixed thumbnail filenames (e.g. image-400x599.jpg) that don't exist on disk — only the base/full-size image was ever downloaded by the scraper.
- Patch: wrote a script to detect this pattern (requested filename minus its -WIDTHxHEIGHT suffix matches an existing base file) and physically copy/duplicate the base image to the missing thumbnail filename.
- LESSON: WordPress generates many resized copies of every uploaded image; a site scraper will often only capture the sizes actually referenced on scraped pages, missing srcset variants. Always check for this specific failure signature (filename pattern with dimension suffix) rather than assuming all 404s share one root cause.

## 6. A duplicated path segment bug recurred multiple times across different batches
- Symptom: certain images repeatedly 404'd with a URL containing a doubled path segment, e.g. .../al_opt_content/IMAGE/secure-house.co.uk/legacy-assets/... (should have been a single clean /legacy-assets/... path).
- Root cause: a WordPress image-optimization plugin (al_opt_content) had ALREADY rewritten some image URLs into a nested "optimizer cache" path BEFORE our own rewrite script ran, so our rewrite script's find/replace pattern matched against an already-modified URL, producing a doubled/nested result.
- Patch: had to specifically detect and collapse this doubled pattern in a follow-up fix, applied repeatedly across new batches of pages as they were built, since each new page-building script reintroduced the same unhandled case.
- LESSON: any newly-written page-building/URL-rewriting script needs to inherit ALL previously-discovered edge cases (this one included) — don't let each new batch script start from a naive/simpler version of the rewrite logic and rediscover old bugs.

## 7. Copyright/attribution-safe content handling was maintained throughout, but "spam vs legitimate" filtering required MULTIPLE passes, not one
- First pass: filtered spam links using an obvious keyword blocklist (casino, bet, kasyno, etc.) — this caught the majority.
- Later, entire new PAGES (not just links) were discovered that were spam-injected articles (e.g. gambling blog posts with innocent-sounding slugs that happened to match legitimate industry keywords like "home" or "security" in a keyword-based filter).
- Patch: had to add a SECOND layer of verification — actually reading each candidate page's title/body text, not just filtering by URL keywords — before deciding to migrate it.
- LESSON: keyword-based URL filtering alone is insufficient for detecting spam/hacked content; always verify actual page CONTENT (title + body text sample) for any page whose legitimacy is uncertain, especially when the source site is known to have been compromised.

## 8. Large binary files (video) broke git pushes multiple times, in multiple ways
- First failure: GitHub's 100MB single-file limit rejected a push containing a 244MB video, requiring Git LFS setup.
- Second failure: after LFS setup, the regular git push (non-LFS objects) failed with "unable to rewind rpc post data" — fixed by increasing http.postBuffer.
- Third failure: push then failed with HTTP 408 (timeout) over HTTPS — root cause was an unstable network connection combined with a large payload, not a git configuration issue.
- Final fix: switched from HTTPS remote to SSH remote entirely, which succeeded reliably on retry.
- LESSON: when pushing large binaries fails, systematically rule out (in order): file size limit → LFS needed; buffer size → increase http.postBuffer; network stability → retry, and if still failing, switch HTTPS→SSH since SSH is generally more robust for large/long-running git transfers.

## 9. A "site inaccessible" scare was actually a stale local dev server, not a code bug
- Symptom: after a batch of changes, the site appeared completely broken/blank in the browser.
- Root cause: a background npm run start process (serving an old build) was still holding the same port a fresh npm run dev was trying to use, causing a collision and serving stale/broken output.
- Patch: killed all node processes on the relevant ports (3000, 3001) and started a single fresh dev server.
- LESSON: "the whole site suddenly doesn't load" is not automatically a code regression — always check for port collisions / duplicate running dev servers FIRST, before deep-diving into recent code changes as the cause.

## 10. Committing was not happening consistently during rapid iteration, creating real risk of data loss
- During a long session of rapid prompt-fix-verify cycles, work was being saved to disk but NOT committed to git for an extended period. When a later step needed to check git history for a specific file, it appeared "missing" — causing a genuine scare that hours of work had been lost.
- The files were NEVER actually lost (disk saves are separate from git commits), but the lack of regular committing made this impossible to quickly verify, and wasted significant time.
- LESSON: commit to git after every meaningfully complete, verified change — not just at the end of a long session. "I'll commit later" during rapid iteration is a real risk, not just a style preference.

## 11. "Build passes" was repeatedly mistaken for "the fix actually works"
- Multiple times throughout this project, a fix was reported as complete based solely on `npm run build` exiting with code 0, without an actual visual/functional check — and the fix later turned out to be incomplete, absent, or to have introduced a new regression (invisible text, duplicate menu, missing images).
- LESSON: `npm run build` passing only proves the code COMPILES. It proves nothing about whether the intended visual or functional change actually happened. Every fix claim must be paired with an explicit visual check (screenshot, manual click-through) or a concrete before/after count/measurement — never accept "build passed" alone as proof of a fix.

## 12. Large batch scripts should always be piloted on a small sample first
- Every time a script was run across all ~100-190 files in one shot without piloting first, at least one edge case was missed and had to be patched afterward in a second pass (see items 3, 5, 6 above).
- LESSON: for any new large-batch transformation, ALWAYS run it on 3-5 representative files first, manually verify the output, THEN scale to the full batch. This is now a hard rule for Phase A onward (see PLAN.md).

## 13. A hidden (off-screen) black-hat SEO spam injection survived all prior spam-cleanup passes because it produced zero visible symptoms
- Symptom: none visible — the homepage (`app/content.html`) looked and rendered completely normally. This was found only via a deliberate proactive audit (checking for `<script>` tags, external domains, and inline obfuscation patterns), not because anything appeared broken.
- Root cause: the injected content was a `<div class="sfb-anchor" style="position:fixed;...z-index:-9999;">` wrapper containing a `<style>` block plus a nested `<div id="sfb-block-...">` pushed off-screen via `left:-9000px !important`. Because the text was never visible on screen, it was invisible to every prior spam-removal pass in item 7 above (which relied on visually/keyword-scanning rendered pages and URL slugs) — this variant hides via CSS positioning, not via a fake page or an obvious spam link in visible content.
- The hidden text itself was steroid/PED affiliate spam ("Bodybuilding School... Best steroid vendor - comprar anabolizantes") with outbound links, classic negative-SEO link-injection: invisible to visitors, crawlable by search engines.
- It was confined to a single file (`app/content.html`, the homepage) — a repo-wide grep for the class name, the id prefix, and two of the spam page's exact link domains/phrases confirmed zero other occurrences across all 193 `content.html` files.
- Patch: deleted the entire 17-line wrapper (anchor div + style block + spam content div) as one atomic, brace-balanced removal; confirmed with `npm run build` (0 errors, all 199 routes still generate) and by grepping the compiled `.next/server/app/index.html` output for the same markers (0 matches) plus confirming adjacent legitimate content (hero heading, video testimonial) still rendered.
- LESSON: "spam content" cleanup on a hacked/compromised site must explicitly include a pass for CSS-hidden content (`display:none`, `visibility:hidden`, `text-indent:-9999px`, `opacity:0`, off-screen `position` with large negative `left`/`top`, `clip:rect(0)`) with actual text extracted from matching elements — not just visible-page/URL-slug scanning (item 7) or `<script>`-tag/external-domain scanning. A compromised site can carry multiple independent injection techniques simultaneously, and clearing one (spam pages/links) does not imply the others (hidden CSS text) are also gone. This should be a standing checklist item any time "spam removed" is claimed for a migrated hacked site (see PROGRESS.md item "190+ pages migrated, spam removed, verified" — that claim predates this finding and was incomplete).

## 14. Item 2's data-bg lazy-load fix had never been applied to `<span>` elements or to elements carrying a `data-bg-small` responsive-background attribute
- Symptom: during a 30-page content/image audit, 14 pages still had visibly blank backgrounds even though most pages had already been through the item-2 `data-bg`→`style` conversion pass.
- Root cause: the original conversion script only ever matched `<div>` tags with a plain `data-bg`/`data-bg-url` pair. Two edge cases slipped through: (a) Fusion Builder sometimes puts the lazy-bg attributes on a `<span class="fusion-column-inner-bg-image">` instead of a `<div>`, and (b) some columns carry a `data-bg-small` attribute (a separate image for small viewports) alongside `data-bg`/`data-bg-url`, with attribute order varying between elements.
- Patch: broadened the conversion regex to match both `<div>` and `<span>`, made it tolerant of attribute order/extra attributes, and added `data-bg-small` localization as its own step.
- LESSON: same lesson as item 6 — a fix written against one observed HTML shape will miss sibling shapes the theme also generates. When re-running an established "known pattern" fix on new pages, re-verify the fix's regex/matcher against a fresh sample from each new page rather than assuming the old matcher's coverage was complete.

## 15. Windows' 260-character path limit breaks `git add`/`git commit`, not just file copies
- Symptom: after downloading two scraped images with very long original WordPress filenames (~180+ characters) to fill gaps from item 5, `git add` failed with "Filename too long" even though the files existed on disk and were readable.
- Root cause: item 4 already documented this limit breaking scraper *copy* operations (fixed there with the `\\?\` long-path prefix for file I/O), but `git.exe` on Windows hits the same 260-char `MAX_PATH` ceiling independently for its own working-tree operations, and that is not something `\\?\`-prefixed Python file I/O can work around — git itself has to be able to open the path.
- Patch: renamed the two offending files to short, still-descriptive filenames and updated their single `content.html` reference each, rather than reconfiguring git (`core.longpaths`) — repo-wide git config changes are out of bounds for an assistant/agent to make unilaterally.
- LESSON: a long scraped filename that merely exceeds Windows' path limit during a file copy will resurface as a *second*, separate failure at `git add` time even after the file-copy workaround succeeds. Treat "file exists on disk" and "git can track this path on Windows" as two different things to verify, and prefer shortening the filename over touching git configuration.

## 16. The PRODUCTS mega-menu portal rendered as a normal, visible block on every page when closed, not just when open
- Symptom: user reported "something wrong with the footer" on every page. Visually the real Footer.tsx content looked fine, but there was extra, oddly-placed text (submenu items like "FUEGO FIRE", "Explore door styles", the mega-menu's contact row) appearing right after it, and every page was ~480px taller than its real content.
- Root cause: the full-screen mega-menu panel is rendered via `createPortal(..., document.body)` in Header.tsx. Its wrapper div only ever got a `className="mobile-menu-active"` (which supplies `position:fixed`, full-screen sizing, and the taupe background) when the menu was open. When closed, the wrapper had `className=""` — no positioning, no background, but also **no `display:none`** — so it rendered as an ordinary, fully-visible, full-width ~480px block at the very end of `<body>`, after the Footer, on every single route (since Header is shared via layout.tsx).
- Found by directly comparing the live site vs localhost footer in the browser (per user's explicit instruction to use the browser, not just fetch text): scrolling to the bottom of any localhost page showed this extra block; the live site did not have it.
- Patch: added `style={menuOpen ? undefined : { display: 'none' }}` to the portal wrapper so it's only ever visible while the menu is actually open.
- LESSON: a portal rendered unconditionally into `document.body` needs an explicit hidden/closed state, not just a positive "active" state. CSS classes that only add styling when a condition is true leave the element in a plain, unstyled — but still visible and still taking up layout space — state when the condition is false. This is a different failure mode from the earlier stacking-context bug (see components/Header.tsx history): that one made the menu invisible when it should show; this one made it visible when it should hide.

## 17. Item 7/13's spam cleanup missed spam links embedded inside WordPress "next/previous post" navigation widgets
- Symptom: scanning all 194 pages for spam keywords (not just the 40 already deep-audited) turned up 2 pages — `3-point-locking` and `side-hinged-garage-doors-types-maintainace-advantages` — whose auto-generated "Previous"/"Next" post-navigation link pointed at an injected French-language gambling article (`les-coulisses-du-live-casino-...`); one of the two links used an absolute `https://secure-house.co.uk/...` URL, meaning a visitor clicking it would leave this site entirely and land on the live, still-compromised WordPress site.
- Root cause: WordPress auto-populates "next/previous post" links by chronological adjacency in the posts table, not by a page's own content — so a spam-injected post sitting next to a legitimate one in publish order gets silently pulled into that legitimate page's navigation widget, with no spam keywords anywhere in the *linking* page's own visible content to catch it. All prior spam passes (items 7 and 13) only scanned each page's own content/URL, so this category slipped through everywhere.
- Patch: removed just the offending `<div class="fusion-tb-previous">`/`<div class="fusion-tb-next">` block matching the exact spam URL on each of the 2 affected pages, leaving the other (legitimate) prev/next link on each page untouched.
- LESSON: when scanning a page for spam, matching against that page's own body text/URL is not enough — auto-generated widgets (post navigation, "related posts," tag clouds) pull content from elsewhere in the CMS and can carry spam that never appears in the page's authored content. Worth a dedicated grep across the whole site for `fusion-tb-previous`/`fusion-tb-next` (and similar auto-populated widget classes) against the known spam-post slug list, independent of any other spam pass.

## 18. Disk ran out of space mid-build (`ENOSPC`), traced to the disposable `.next` build cache
- Symptom: `npm run build` failed outright with `Error: ENOSPC: no space left on device` while writing a `.next/server/app/.../_index.segment.rsc` file, partway through a build that had succeeded cleanly several times earlier in the same session.
- Root cause: the machine's C: drive was at 100% capacity (200GB total, ~1.2GB free) — not a project-specific issue, a machine-wide one. The `.next` directory alone (Next.js's build output/cache, fully regenerated on every build, never meant to be committed) had grown to 3.5GB.
- Patch: deleted `.next` (`rm -rf .next`), which freed 3.5GB and let the build complete normally. This is always a safe operation — `.next` is disposable build output, not source.
- LESSON: `ENOSPC` during a build is a disk-space problem, not a code problem — check `df -h` (or equivalent) before debugging the build itself. Deleting `.next` is a safe first response, but it is a *temporary* fix for a *machine-wide* problem (1.2GB free on a 200GB drive is critically low regardless of this project) — flagged to the user rather than treated as resolved, since only they can see what else is consuming space on their machine (this is unrelated to git and outside anything this migration project controls).

## 19. Another AI tool ("Antigravity") "fixed" the invisible /projects header by inverting its filter, which papered over the real bug instead of fixing it
- Symptom (reported by user): the `/projects` page header and post-card filter tabs (All/Commercial/Residential) were invisible.
- Root cause 1 (header): `Header.tsx`'s nav row uses Avada's `fusion-absolute-container` styling, i.e. `position: absolute`, meant to float the header on top of a tall dark hero image. `/projects` has no hero image — a light/white page — so the absolutely-positioned row (a) contributes 0 height to its parent, letting page content occupy the same box and paint over it, and (b) its text/logo color variable (`--awb-color1`, resolving to `#ffffff`) is meant for a dark background, so even where visible it would be white-on-white. Antigravity's attempted fix (`components/Header.tsx`, an `isLightPage` branch) applied `filter: invert(1) hue-rotate(180deg)` to `.fusion-tb-header` — this can only recolor pixels that are actually painted, so it did nothing about the underlying 0-height/paint-order collapse, and the header stayed invisible.
- Root cause 2 (filter tabs): Avada's own dynamic CSS (`public/legacy-assets/uploads/fusion-styles/0641d0f1c6e8126c14e3ff8f5cde061e.min.css`) sets `.fusion-filters{display:none}` unconditionally, and only overrides it to `display:block !important` inside `@media (max-width:800px)` — i.e. the desktop reveal was always done by WordPress/Avada's own JS adding a class, never by CSS alone. Same failure family as item 2 in this log (JS-driven UI that never runs in the static export) but for an element class we hadn't audited before.
- Patch: replaced the `filter: invert()` hack in `Header.tsx` with an `isLightPage`-scoped override that (a) sets `.fusion-tb-header .fusion-builder-row-1/-2 { position: relative !important }` so the header participates in normal flow and reserves real space, (b) gives `.fusion-tb-header` an opaque white background, (c) redefines `--awb-color1` to a dark tone scoped to the header only (doesn't leak to the rest of the page, which still uses white for on-hero contexts), and (d) inverts just the raster logo `<img>` elements (they don't respond to CSS variables). Separately added an unconditional `.fusion-filters{display:flex !important;}` in `app/layout.tsx`'s existing override `<style>` block, since the filter-tabs bug isn't specific to `/projects` — any page using a Fusion post-cards grid has the same defunct-JS-reveal problem.
- LESSON: a `filter: invert()`/color-only fix on an element that isn't actually rendering (0 height, painted-over, or `display:none`) is a no-op dressed up as a fix — always confirm with `getBoundingClientRect()`/computed `display` that the element occupies real, unobstructed space *before* reaching for a color/contrast patch. And per item 2's lesson: any element whose visibility historically depended on WordPress/Avada's own runtime JS (not just lazy-load images) needs to be re-audited per new page/component discovered, not assumed already covered.

## 20. The pure-JSX pilot conversion (`/doors/fire-resistant-doors-v2/`) silently lost `fusion-body` from the real `<body>` element, breaking Header/Footer styling that every unconverted page depends on
- Symptom: on the JSX-converted pilot page, the shared `<Footer/>` copyright line rendered left-aligned and at a visibly larger font size instead of centered/13px, even though `components/Footer.tsx` was completely unchanged and identical on both the old and new page.
- Root cause: every unconverted page's `content.html` contains a full, raw `<!doctype html><html><head>...<body class="wp-singular ... fusion-body ...">` document, dumped via `dangerouslySetInnerHTML` into a `<div>` that is itself inside the *real* `<body>` from `app/layout.tsx`. A document can only have one `<body>` element, so browsers resolve this the way they resolve any duplicate/nested `<body>` tag found during parsing: they don't render a second one — they **merge that tag's attributes (including `class`) onto the real, already-existing `<body>` element.** This is silent and easy to miss: `document.body.className` on every current page carries the *entire* scraped Avada class list, including `fusion-body`, purely as a side effect of this parser behavior, not because anyone put it there on purpose. A real CSS rule in the page's compiled Avada stylesheet, `.fusion-body .fusion-title-center .title-heading-center{text-align:center}`, depends on that class being present on an ancestor of `<Footer/>` and `<Header/>` — which only works because it lands on the *real* `<body>`, since Header/Footer are siblings of the page content in `app/layout.tsx` (`<Header/>{children}<Footer/>`), not descendants of it. A clean JSX conversion correctly never renders a literal `<body>` tag inside its content (React only allows the one in `layout.tsx`), so this merge never happens, `fusion-body` never reaches the real `<body>`, and every `.fusion-body`-scoped rule in that ~6,700-rule stylesheet stops matching anywhere on the page — silently, with no console error, only a visual diff.
- Patch: moved the shared portion of that Avada body-class string (everything except the per-page `page-id-XXXX`/`page-child`/`parent-pageid-XXXX` tokens, which don't drive this) onto the real `<body>` tag in `app/layout.tsx` directly, applied globally to every page. Confirmed harmless on still-unconverted pages (they now carry the class twice — once from `layout.tsx`, once from the merge side-effect — duplicate class tokens are a no-op) and confirmed it fixes the pilot page's Footer rendering.
- LESSON: **this must be treated as a required, unskippable step at the start of any further page's JSX conversion, not something to re-derive per page** — the fix in `layout.tsx` is global and already done, so no future page conversion should reintroduce this bug, but if `layout.tsx`'s `<body>` className is ever changed for other reasons, re-verify a converted page's Header/Footer against an unconverted page's before assuming it's still fine. More generally: when a "shared" component (Header/Footer, or anything else rendered as a sibling of page content rather than a descendant) renders differently on a converted vs. unconverted page despite the component's own code being byte-identical, suspect a difference in *ancestor* context (attributes/classes on `<html>`/`<body>` or another shared wrapper) before suspecting the component itself — check `document.body.className` (and any other shared ancestor) on both pages side by side.

## 21. TypeScript rejects real, valid scraped markup during JSX conversion in a few narrow, recurring ways — none are conversion bugs, all need a fix in the converter itself (not per-page)
- Symptom: `npx tsc --noEmit` failures during the JSX-conversion rollout (`scripts/html_to_jsx.js`) that aren't wrong output, just TypeScript's stricter-than-HTML typing:
  1. `text-align: var(--awb-content-alignment)` (and other strict-enum CSS properties like `whiteSpace`, `position` whose value is a `var()` reference instead of a literal keyword) — valid CSS, but TS's `CSSProperties.textAlign` type is a closed string-literal union that doesn't include arbitrary `var()` strings, so even `as React.CSSProperties` is rejected as "neither type sufficiently overlaps."
  2. `aria-level="5"` (and the other numeric ARIA attributes: `aria-valuemax`, `aria-valuemin`, `aria-valuenow`, `aria-colcount`/`-colindex`/`-colspan`, `aria-rowcount`/`-rowindex`/`-rowspan`, `aria-setsize`, `aria-posinset`) — React types these specific ARIA attributes as `number`, unlike every other ARIA/HTML attribute which is `string`, so passing the scraped string value fails.
  3. `<lite-youtube>` (found on `tracless-garage-doors`) — a real custom element (any tag name containing a hyphen is valid HTML per the Custom Elements spec), but TypeScript's `JSX.IntrinsicElements` doesn't know about any custom element unless it's explicitly declared.
- Patch: (1) route the style-object cast through `as unknown as React.CSSProperties` instead of a direct cast — the same fix TS's own error message suggests; (2) detect the known numeric-ARIA attribute names and emit them as a numeric JSX expression (`aria-level={5}`) instead of a quoted string; (3) added `types/custom-elements.d.ts`, augmenting `declare module "react" { namespace JSX { interface IntrinsicElements { ... } } }` — note this is the React 19 convention (`React.JSX`), **not** the old classic-runtime bare global `declare namespace JSX { ... }`, which silently does nothing under the `"jsx": "react-jsx"` transform this project uses (tried that first, `tsc` kept failing with no explanation why the declaration wasn't being picked up).

## 22. `scripts/assemble_jsx_page.js` hard-required a `metadata` export that some pages genuinely don't have
- Symptom: converting `/door-styles/french-doors/` (and the other 3 door-styles children: victorian, edwardian, georgian) threw `Error: Could not find metadata block in app/door-styles/french-doors` and stopped the pipeline.
- Root cause: this isn't a scraping/conversion gap — these 4 pages' existing `page.tsx` files never had a `metadata` export in the first place. Matches an already-known, already-logged gap: `PROGRESS.md`'s "Blocked on Client" list has had "Georgian Doors / Georgian Front Doors meta content" on it since before this session, meaning the client hasn't supplied title/description copy for this page family yet. The assembler script assumed every page has metadata and threw instead of handling the absence.
- Patch: made the metadata block optional in `assemble_jsx_page.js` — if the source `page.tsx` has none, the generated `-v2` page also has none (and skips the now-unneeded `import type { Metadata }`), preserving current behavior exactly rather than inventing placeholder copy the client hasn't approved.
- LESSON: a converter/assembler script should mirror a source page's actual structure, including its gaps — "the original doesn't have X" is a valid state to pass through, not an error to throw on. Don't let a batch script assume every page in a family is structurally identical to the ones already converted.

## 23. Converting the 3 special-case pages (`/contact-us/`, `/projects/`, `/`) surfaced one more numeric-attribute gap and confirmed two things that looked risky actually weren't
- **Numeric-attribute gap**: `/contact-us/`'s real `<form>` (never exercised by the first 31 pages, none of which had form fields) hit the same TypeScript-vs-HTML numeric-typing mismatch as item 21's ARIA case, but for plain HTML attributes: `tabindex=""`, `minlength="0"`, and a `<textarea cols/rows>` all failed with "Type 'string' is not assignable to type 'number'" because React types `tabIndex`/`minLength`/`maxLength`/`cols`/`rows` (and `colSpan`/`rowSpan`/`size`, added proactively) as `number`, while HTML treats them as plain text where an invalid/empty value is simply ignored per spec. Extended `NUMERIC_ATTRS` in `html_to_jsx.js` to cover these, and changed the fallback behavior: when a numeric attribute's value doesn't actually parse as a number (e.g. `tabindex=""`), the attribute is now **dropped entirely** rather than falling through to an invalid string render — this matches how a browser already treats an invalid `tabindex` value (ignored), so it's a no-op change in real behavior.
- **False alarm, not a bug**: the converted `<input autoComplete="off" minLength={0} />` renders as literal `autoComplete="0"`/`minLength="0"` (not lowercased to `autocomplete`/`minlength`) in this project's React 19 SSR output, while `tabIndex`/`htmlFor` correctly *do* lowercase. Confirmed via an isolated throwaway test route that this is real, reproducible framework behavior, not a converter bug — and it doesn't matter functionally, because HTML attribute names are case-insensitive when the browser parses them, so `autoComplete="off"` and `autocomplete="off"` produce an identical DOM either way. Don't chase this further if it recurs.
- **`/projects/` needed a structural pattern, not a script change**: `ProjectsClient.tsx` is a `"use client"` wrapper that takes a raw `html` string and injects it via `dangerouslySetInnerHTML`, then attaches filter-tab click handlers to the resulting DOM in a `useEffect` (via `querySelectorAll`, which works identically on any real DOM node regardless of whether React or `innerHTML` created it). For the JSX conversion, created a parallel `ProjectsClientV2.tsx` that takes `children: React.ReactNode` instead of an HTML string and renders `{children}` — the exact same `useEffect`/querySelector logic carries over unchanged, since it only cares about the final DOM shape, not how it got there.
- **Homepage's `HeroSlider` portal target survived conversion untouched, as expected**: `HeroSlider.tsx` uses `createPortal` targeting `document.getElementById('__hero-slider-mount')`, an empty `<div id="__hero-slider-mount">` sitting inside the page content. Since the converter preserves ids exactly, this kept working with zero special-casing — worth remembering for any future page with a similar mount-point pattern.
- **Investigated but deliberately left alone**: a `PROGRESS.md`-flagged item claimed the homepage had two blocks of "dead" leftover slider markup (`.awb-background-slider`, `.tfs-slider.flexslider`) that needed removing during this conversion. Checked both: `.tfs-slider.flexslider` (1 occurrence) is real, live content — a genuine image-gallery slider further down the page, unrelated to the hero. `.awb-background-slider` (1 occurrence) is a small, empty (`swiper-slide` with no image), CSS-hidden-on-medium/large-viewport block sitting right next to the hero mount point — plausibly dead, but removing it requires a real visual check on a small viewport to be sure, which wasn't possible this session (Chrome extension disconnected). Left it in place, converted 1:1 like everything else, rather than guess.
- LESSON: when a page has a "special case" flag from an old session, re-verify the specific claim against current file state before acting on it — line numbers and even the underlying facts can go stale as a file is edited over many sessions (the two flagged blocks were originally noted at lines ~5486/~5602; a head-cleanup pass since then moved them to lines 133/1010, and closer inspection showed one of the two claims was simply wrong).
- LESSON: all three fixes live in the shared converter (`scripts/html_to_jsx.js`) or a shared type-declaration file, not in any individual page's output — so every page converted after this fix automatically gets it for free. When `tsc` rejects scraped markup during this rollout, the default assumption should be "the converter needs a new, generalizable case," not "this one page needs a manual patch" — check whether the same HTML pattern could plausibly appear on other unconverted pages before treating a fix as page-specific. Item 3 specifically: if a future page uses a *different* custom element, it needs its own entry added to `types/custom-elements.d.ts` — the declaration only covers the specific tag names listed in it, not custom elements generally.

## 24. `value`/`checked` on converted form fields triggered React's "read-only field" warning — invisible to `tsc`/`npm run build`, only surfaced by actually loading the page in a browser
- Symptom: no build or type error. Only visible as a Next.js dev-mode "3 Issues" overlay badge when `/contact-us-v2/` was actually opened in Chrome: `"You provided a 'value' prop to a form field without an 'onChange' handler. This will render a read-only field. If the field should be mutable use 'defaultValue'. Otherwise, set either 'onChange' or 'readOnly'."` — once per text/email/phone input (3 total).
- Root cause: the original page's `value=""` (and, if any future page has one, `checked=""`) reaches the browser via raw `dangerouslySetInnerHTML`, which bypasses React's form-field reconciliation entirely — the browser just parses it as an ordinary HTML attribute with no special behavior. The converted JSX page renders the exact same-looking `value=""` as an actual React prop, and React treats *any* element with a `value` (or `checked`) prop and no `onChange` handler as a controlled, permanently-locked field. Since this converter never generates event handlers for anything, every form field it produces would hit this.
- Patch: in `html_to_jsx.js`'s `jsxAttrString`, `value` on `<input>`/`<textarea>` now renders as `defaultValue`, and `checked` (which only ever appears on `<input>` in valid HTML, so safe to rename unconditionally) as `defaultChecked` — the correct uncontrolled-field equivalents, matching what the scraped attribute actually meant (seed a starting value, not lock the field). Verified the fix by setting the DOM value directly and dispatching an `input` event — the field now retains the change instead of any risk of it being forced back.
- LESSON: **this class of bug is invisible to every automated check this project relies on** (`tsc --noEmit`, `npm run build`, and the `scripts/structural_diff.js` count-based comparison all passed cleanly both before and after the fix) — it only appeared once the page was actually loaded in a real browser with React's dev-mode warnings active. This is the concrete argument for why the "pending: pixel-level visual check in an actual browser" caveat on the earlier 14-page and 3-special-page verification batches matters and shouldn't be treated as a formality — a browser check found a real, if low-impact, bug that three layers of automated verification all missed. Any future page with form fields should get an actual in-browser load-and-check, not just a clean build.

## 25. FAQ accordions and "Read more" toggles never worked, sitewide, on 20 pages — Bootstrap collapse markup with no Bootstrap JS
- Symptom: user reported clicking FAQ questions and "Read more" links did nothing, across multiple pages.
- Root cause: Avada compiles its accordion/toggle widget as classic Bootstrap collapse markup — a trigger `<a data-toggle="collapse" data-target="#id" aria-expanded="false">`, and a target panel `<div class="panel-collapse collapse" id="...">`. Each page's own compiled Avada CSS already correctly defines `.collapse{display:none}` and `.collapse.in{display:block}` — that part works. What's missing is Bootstrap's `collapse.js`, which normally listens for clicks on `[data-toggle="collapse"]` and toggles the `.in` class. This migration never pulled in Bootstrap (or any equivalent), so the CSS was always present and correct but nothing ever triggered it — every toggle was permanently collapsed and inert, on every page using this widget (FAQ sections and "Read more" links are the same underlying component, just different trigger label text).
- Scope: 20 pages use this pattern: `doors/bullet-proof-doors`, `doors/communal-entrance-doors`, `doors/fire-resistant-doors`, `doors/high-security-doors`, `doors/panic-room-doors`, `door-styles/edwardian-doors`, `door-styles/french-doors`, `door-styles/georgian-doors`, `door-styles/victorian-doors`, `garage-doors` (hub), `garage-doors/sectional-garage-doors`, `garage-doors/side-hinged-garage-doors`, `garage-doors/sliding-garage-doors`, `garage-doors/tracless-garage-doors`, `grilles-shutters/colllabsible-grilles`, `grilles-shutters/security-shutters`, `security-levels`, `trade`, `windows/high-security-steel-windows`, `windows/security-aluminium-windows`.
- Patch: added `components/AccordionToggle.tsx`, a client component using a single delegated `click` listener on `document` (works for any `[data-toggle="collapse"]` element on any page, including ones matched by future pages, without needing per-route re-initialization the way `ScrollReveal.tsx` does) that: toggles the `.in` class on the target panel, toggles `aria-expanded` on the trigger, and — found by checking the compiled CSS directly rather than assuming — toggles an `.active` class on the trigger too, since the chevron icon swap (`.active-icon`/`.inactive-icon` inside `.fusion-toggle-icon-wrapper`) is keyed off `a.active`/`a:not(.active)`, not `aria-expanded`. Also implements real Bootstrap accordion-group semantics: when a trigger's target has a `data-parent`, opening it closes any other currently-open panel within that same parent (verified: clicking a second FAQ question closes the first one, matching the live site's standard accordion behavior). Mounted globally in `app/layout.tsx`, plus a CSS safety-net (`.panel-collapse.collapse:not(.in){display:none}` / `.panel-collapse.collapse.in{display:block}`) in case any individual page's compiled CSS bundle doesn't happen to define these rules itself.
- LESSON: when a widget's markup includes `data-toggle`/`data-target`/`aria-*` attributes matching a well-known JS framework's plugin convention (Bootstrap, in this case), check whether that framework's JS is actually loaded before assuming the CSS alone should have worked — the CSS being present and correct is not evidence the feature functions; it's exactly the kind of thing that looks broken for a boring, easy-to-fix reason (no click handler) rather than a CSS bug. Also: don't assume the "obvious" state-tracking attribute (`aria-expanded`) is what the CSS actually keys off of — check the compiled stylesheet directly, as this page's icon-swap rule used a different class entirely.

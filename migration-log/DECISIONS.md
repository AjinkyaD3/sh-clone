# Secure House Migration - Architectural Decisions

This document captures architectural decisions and their underlying reasoning. Append new entries as real decisions are made going forward.

- **Styling**: Keep existing Avada/Fusion CSS classes, no Tailwind/CSS Modules switch. 
  - *Reasoning*: Preserves existing visual design and avoids a full visual redesign.
- **Component approach**: Build reusable page-type templates rather than converting pages individually.
  - *Reasoning*: Ensures consistency, maintainability, and significantly reduces the effort required for a ~194 page migration.
- **Conversion order**: Automation-heavy/high-volume first, complex/one-off last.
  - *Reasoning*: Proves the extraction pipeline early and defers complex UI component construction until the foundation is solid.
- **CSS approach (reconfirmed 2026-09-07)**: Continue with plain CSS matching the existing Avada/Fusion design system — no Tailwind, no CSS Modules for the JSX-conversion work. `package.json` has no Tailwind dependency; the only CSS Modules in the repo (`components/HeroSlider.module.css`, `components/BlogPostTemplate.module.css`, `app/blog/page.module.css`) are scoped to the already-fully-JSX blog system and the new HeroSlider component, not a signal to switch approach site-wide.
  - *Reasoning*: Reconfirms the original styling decision above. As the pure-JSX conversion (see PLAN.md) starts touching the highest-traffic pages, introducing a second styling system (Tailwind utility classes) alongside 190+ pages of hand-tuned Avada/Fusion CSS and `!important` overrides (see `app/layout.tsx`) would create two parallel, inconsistent styling vocabularies in the same codebase — harder to maintain, harder for the next person to reason about which system "wins" on a given element, and no visual upside since the target is pixel-parity with the existing design, not a redesign.
  - *How to apply*: New JSX-converted pages/components should use plain CSS (global stylesheet or component-scoped `.module.css`, following the HeroSlider precedent) with class names and values lifted directly from the page's existing Fusion markup/CSS variables, not reimplemented in a utility-class or Tailwind idiom.

## 2026-09-07 (later) — Scope decisions for the 31-page clean rebuild

These four entries confirm the concrete rules for tomorrow's execution on the 31-page family scoped in PLAN.md. They were decided together and should be read as a set.

- **Visual scope: clean rebuild, not a redesign**.
  - *Decision*: The 31-page conversion keeps the same overall visual design/layout as today's site. Small, low-risk UX polish is welcome where obviously beneficial (same spirit as tonight's hover-state and text-legibility fixes), but no structural changes, no new sections, and no major layout shifts.
  - *Reasoning*: The goal is a clean, maintainable codebase behind the design the client has already approved — not a design refresh. Keeping visual scope frozen also makes before/after verification unambiguous (pixel-parity is the bar, not "does this look better").
  - *How to apply*: Before writing a page's JSX, treat its current rendered output (live site or today's working `content.html` render) as the visual spec. Flag any polish opportunity to the user rather than taking it unilaterally if it touches layout, spacing, or structure rather than pure legibility/contrast/hover-state fixes.

- **Code cleanliness: zero trace of scraped HTML in rebuilt pages**.
  - *Decision*: Rebuilt pages must contain no leftover Avada/Fusion classNames, no old scraped comments, and no `dangerouslySetInnerHTML`. Full clean, semantic JSX, authored from the page's actual content — not copy-pasted structure from `content.html`.
  - *Reasoning*: A structural extraction that just re-wraps Avada markup in JSX (which is what the site has today) inherits all of Avada's fragility — the absolute-positioning bugs, the `!important` override pile in `app/layout.tsx`, the JS-dependent-visibility traps documented across MISTAKES-AND-PATCHES.md. A genuine rebuild is the only way to actually stop accumulating that debt on the pages we touch.
  - *How to apply*: When a rebuilt page ships, `grep` it for `dangerouslySetInnerHTML`, `fusion-`, `awb-`, and `avada-` class prefixes — zero matches is the acceptance bar. Content (copy, image paths, links) is still sourced from the existing `content.html`/live site; only the markup/class implementation must be original.

- **CSS approach: CSS Modules, plain CSS syntax — supersedes the original "keep existing Avada/Fusion CSS classes" decision**.
  - *Decision*: The 31-page rebuild uses CSS Modules (one `ComponentName.module.css` per component), written in plain CSS syntax. No Tailwind.
  - *This explicitly supersedes* the original styling decision at the top of this file ("Keep existing Avada/Fusion CSS classes, no Tailwind/CSS Modules switch") **and** the "reconfirmed 2026-09-07" entry directly above this one, both of which said to keep using the existing Avada/Fusion CSS. Neither of those decisions is wrong for what it was scoped to at the time — they're both preserved above, not deleted, so the history of "we considered this and chose X, then later changed to Y" stays legible.
  - *Reasoning it changed*: Both earlier entries were written when the plan was a **structural HTML extraction** — port the existing Avada markup into JSX wrappers, keep its CSS classes, minimize risk by minimizing change. Today's plan for these 31 pages is different in kind: a **genuine clean rebuild** (see the code-cleanliness decision above) with zero Avada/Fusion classNames surviving. Once the classNames are gone, "keep the existing CSS classes" is no longer a coherent instruction — there's nothing left to keep. CSS Modules were chosen over both the old approach and over Tailwind because: (a) they keep styling in plain, portable CSS — the same language the rest of the still-unconverted 160+ pages use, so no `!important`-battling utility classes get introduced into a codebase that already fights specificity wars (see `app/layout.tsx`); (b) they give each rebuilt component real style isolation without hand-namespacing class names; (c) there's already a working precedent in this repo (`components/HeroSlider.module.css`, `components/BlogPostTemplate.module.css`, `app/blog/page.module.css`) so this isn't a new tool, just a wider application of one already proven here.
  - *How to apply*: Every new component gets its own `ComponentName.module.css`. Colors, spacing, and typography values are still lifted from the page's current rendered design (per the visual-scope decision above) — CSS Modules changes *how* the styles are organized and scoped, not what they render as. This decision applies to the 31-page family in PLAN.md; the ~160 pages still queued behind it are unaffected until they're scoped for their own conversion pass.
